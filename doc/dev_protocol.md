# 递归式 AI 协同开发协议 (Recursive Co-Dev Protocol)

本协议通过六阶段流水线与嵌入式 QA 对抗，确保 AI 开发的代码达到生产级稳定性。

---

## 第一阶段：需求明确 (Requirement Clarification)
- **任务**：AI 需主动提出 3 个最关键的澄清问题。
- **目标**：明确业务边界、数据模型与非功能性需求。

## 第二阶段：架构与契约设计 (Architect & Contract Design)
- **任务**：输出 Markdown 架构文档。
- **要求**：必须定义 Pydantic 数据模型、接口契约及资源生命周期管理。

## 第三阶段：对抗性迭代 (Adversarial Feedback Loop)
- **任务**：加载 `@docs/qa_agent.md` 逻辑，进行 3 轮循环：
    1. **Agent QA (Red Team)**：调用 QA Agent 的视角，对方案进行“生产环境崩溃预判”。
    2. **Agent Dev**：根据 QA 报告，严厉批判并更新设计。
- **目标**：消除 95% 的逻辑漏洞。

## 第四阶段：稳定性保障 (Stability Assurance)
- **测试先行 (TDD)**：编写 `pytest` 用例，覆盖边界条件、空值、异常输入。
- **风险报告**：输出回归影响分析。

## 第五点五阶段：回归影响评估 (Regression Impact Analysis)
- **任务**：在代码提交前，AI 必须基于代码变更（Git Diff 视角）进行“影响范围推演”。
- **强制交互**：
    1. **依赖树分析**：AI 需列出：本次修改涉及的函数/类，以及它们被哪些其他模块引用？
    2. **场景关联**：AI 需评估：“针对该模块，我是否遗漏了以下场景的测试：
        - [ ] 核心 API 路径（是否影响旧版业务？）
        - [ ] 外部依赖（如果我修改了工具调用逻辑，是否影响 Prompt 注入？）
        - [ ] 边界联动（此改动是否会导致下游解析器崩溃？）”
    3. **测试执行**：AI 必须编写或运行特定的集成测试 (Integration Test) 来模拟上述联动场景，确保“不破坏旧有功能”。

## 第六阶段：最终审计 (Final Audit)
- **审计 AI**：全方位评分 (0-10)。
- **债务清单**：明确指出技术债务与建议修复路径。
